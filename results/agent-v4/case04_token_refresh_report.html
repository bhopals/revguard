CRITICAL 1. UPDATE statement missing WHERE clause extends every session in the table
ledgerly/auth.py:70 · correctness
The UPDATE in refresh_token has no WHERE clause: `db.execute("UPDATE tokens SET expires_at = ?", (...,))`. It sets expires_at on every row in the tokens table, not just the row for the token being refreshed. Concrete scenario: user A logs in and later has their token expire naturally; user B calls refresh_token with their own valid token. Because the UPDATE has no filter, user A's already-expired (or soon-to-expire) token row is also rewritten with a fresh expiry, silently reviving/extending sessions for every other logged-in user (or previously-expired-but-not-yet-purged rows) in the system. This should be `"UPDATE tokens SET expires_at = ? WHERE token = ?"` with the token bound as a second parameter.

MAJOR 2. Test only checks trivial return value, never verifies the actual expiry side effect or token scoping
tests/test_ledgerly.py:60 · test-adequacy
test_refresh_token only asserts `auth.refresh_token(db, token) == token`. Looking at the implementation (ledgerly/auth.py:65-73), refresh_token unconditionally returns the same token it was given as long as authenticate() doesn't raise — so this assertion is guaranteed to pass regardless of whether the expiry was actually extended, or even whether the UPDATE statement is correct at all. The test never queries the tokens table to confirm expires_at was moved forward, and it uses only a single token in the database, so it cannot detect that the UPDATE statement in auth.py:70 has no WHERE clause and therefore blindly rewrites expires_at for every row in the tokens table (i.e., refreshing one user's token silently extends every other logged-in user's session too). A test that created two tokens (e.g., for two different users), called refresh_token on only one, and then asserted the other token's expiry was unchanged would have caught this; as written, the test provides no coverage of the feature's actual behavior.
