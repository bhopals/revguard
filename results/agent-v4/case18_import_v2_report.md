# Code review: Importer v2: category mapping and atomic batches

> Statement import learns two things users kept asking for: map merchant descriptions to categories (case-insensitive prefix rules, e.g. 'COFFEE' -> food), and all-or-nothing batches so a bad row no longer leaves a half-imported statement. Duplicate detection was also simplified and sped up by keying on (date, amount).

**Verdict: request changes.** 6 blocking finding(s), 1 critical.

## 1. [CRITICAL] Atomic batch guarantee is broken: add_expense commits each row individually inside the outer transaction

`ledgerly/importers.py:112` — correctness

import_statement wraps the row loop in `with db.transaction():` (line 107) and its docstring promises 'if any row cannot be imported, no expense from this statement is recorded.' However, add_expense() (ledgerly/expenses.py:24) inserts via db.execute(), and Database.execute() (ledgerly/db.py:126-129) itself opens its own `with self.transaction():` and calls self.conn.commit() right after the INSERT. Since sqlite3 has no real nested-transaction concept here, that inner commit() commits the *entire* currently-open transaction immediately, including this row, permanently, before the loop even reaches later rows. Concrete failure: call import_statement with category_map={'COFFEE': 'food', 'GROCER': 'yachts'} on a statement whose first row is 'COFFEE CO' and second row is 'GROCER LTD'. Row 1 succeeds and is committed to disk by add_expense's internal commit. Row 2's category_for() raises ImportError_('yachts' not in VALID_CATEGORIES), which propagates out of the loop; the outer `with db.transaction()` except-clause calls conn.rollback(), but there is nothing left to roll back because row 1 was already committed by the nested call. The result is a partially-imported statement (the food expense for COFFEE CO persists) with no import_batches audit row at all (the INSERT at line 115 is never reached) — the exact opposite of the 'all-or-nothing' behavior the PR title and docstring claim. The existing test (test_mapping_to_unknown_category) only exercises the case where the very first row fails, so it never surfaces this bug.

*Verified: Read ledgerly/db.py: Database.execute() wraps its single INSERT in its own `with self.transaction():` block, which calls self.conn.commit() unconditionally on success (lines 126-129, transaction() at 109-116) — sqlite3 has no real nested transactions, so this commits the whole connection state, not just the row. add_expense() (expenses.py:24) calls db.execute() for its INSERT. Reproduced the exact scenario from the finding: called import_statement(db, user, statement_with_2_rows, category_map={'COFFEE':'food','GROCER':'yachts'}) inside the outer `with db.transaction()` in importers.py.*

## 2. [MAJOR] test_atomic_batch never exercises a failure — cannot detect broken atomicity

`tests/test_importers.py:68` — test-adequacy

TestAtomicity.test_atomic_batch (lines 69-74) only imports a fully valid STATEMENT and checks the success counts and batch row, identical in substance to the pre-existing TestImport.test_import_and_reimport. It never triggers a mid-batch failure (e.g. a bad row, a category-mapping error on a later row, or an add_expense validation error), so it would pass unchanged even if `with db.transaction():` in import_statement were deleted entirely, or if rollback silently failed to undo prior inserts. The PR's headline claim — 'a malformed row no longer leaves a half-imported statement behind' — has zero coverage. In fact, add_expense() calls db.execute(), which itself opens its own `with self.transaction(): ... self.conn.commit()` (ledgerly/db.py:126-129) on every row, committing each insert to the underlying sqlite3 connection as it happens; the outer transaction in import_statement (importers.py:107) therefore cannot roll back rows already committed by earlier iterations if a later row fails. No test in this PR would catch that the atomicity guarantee is broken for any statement where a later row fails after an earlier row succeeded.

*Verified: Read ledgerly/db.py, expenses.py, importers.py, and tests/test_importers.py. Confirmed db.execute() (used by add_expense) wraps every call in its own `with self.transaction(): ... self.conn.commit()`, which unconditionally commits the underlying sqlite3 connection regardless of the outer `with db.transaction():` in import_statement — there are no savepoints, so nested transaction() calls defeat the outer rollback.*

## 3. [MAJOR] test_mapping_to_unknown_category only checks the exception, never checks DB state, and fails on the first row so it cannot expose the partial-commit bug

`tests/test_importers.py:62` — test-adequacy

test_mapping_to_unknown_category asserts only that ImportError_ is raised; it never queries the expenses or import_batches tables afterward to confirm nothing was persisted. Additionally, because category_map={'COFFEE': 'yachts'} matches the very first parsed row (COFFEE CO), category_for() raises before any add_expense call executes, so this test happens to pass even though (per db.py's non-nested transaction handling) any row that succeeds before the failing one would already be durably committed. A category map that fails on a later row (e.g. mapping STREAM, which appears last, to an invalid category after COFFEE/GROCER already succeeded) combined with an assertion that db.query('SELECT * FROM expenses ...') returns no rows would have caught that import_statement leaves partial data behind on failure — exactly the regression this PR claims to fix.

*Verified: Read db.py: Database.execute() opens its own nested `with self.transaction(): ... self.conn.commit()`, and expenses.add_expense() calls db.execute() for each insert. This means each row committed inside the outer `with db.transaction():` in import_statement is actually committed immediately per-row, not held until the batch's final commit.*

## 5. [MAJOR] Docstring promises atomic all-or-nothing import, but each expense insert is committed individually and survives rollback

`ledgerly/importers.py:107` — correctness

`import_statement` wraps the loop in `with db.transaction():` and the docstring (line 100-103) explicitly states the batch is all-or-nothing and 'no expense from this statement is recorded' if any row fails. But each row is written via `add_expense` -> `db.execute` (ledgerly/expenses.py / ledgerly/db.py:126-129), and `Database.execute` itself opens its own `with self.transaction():` and calls `self.conn.commit()` immediately after every insert (ledgerly/db.py:110-116). Because sqlite3 commits are connection-wide, each row's commit is not deferred to the outer transaction — it is durably written the moment `add_expense` returns. If a later row fails (e.g. `category_for` raises `ImportError_` for a mapping to an invalid category at line 84, or `add_expense` raises `ExpenseError` for a too-long note), the exception propagates up to the outer `with db.transaction():` block, whose `except` clause calls `self.conn.rollback()` — but there is nothing left to roll back, since the prior rows already committed individually. The result is a half-imported statement with no `import_batches` row recorded for it, which is exactly the failure mode this PR claims to have fixed. Example: a 3-row statement where row 1 and 2 map to valid categories and row 3 maps to an unknown category via `category_map` will leave rows 1-2 permanently in `expenses` even though `import_statement` raises. The existing test (`TestAtomicity.test_atomic_batch`) never exercises a failure case, and `test_mapping_to_unknown_category` happens to fail on the very first row, masking the bug.

*Verified: Read ledgerly/db.py: Database.transaction() commits/rolls back the shared sqlite3 connection, and Database.execute() wraps every single statement in its own with self.transaction() call, committing after each insert. add_expense -> db.execute inherits this. Reproduced directly: built a 3-row statement where row 3 maps to an invalid category via category_map (triggering ImportError_ in category_for at line 84), called import_statement inside a fresh in-memory Database.*

## 6. [MINOR] category_for is not actually case-insensitive with respect to the mapping keys, contradicting its docstring

`ledgerly/importers.py:82` — correctness

The docstring (lines 78-79) and the module docstring (lines 9-10) both describe the feature as 'case-insensitive prefix rules', implying a caller can supply prefixes in any case. The implementation only uppercases `desc` (`desc.upper().startswith(prefix)`) and never normalizes `prefix`, so a mapping such as `{"Coffee": "food"}` or `{"coffee": "food"}` will silently fail to match `'COFFEE CO'` and the row falls back to `DEFAULT_CATEGORY` with no warning or error. This is a real trap for API callers who build `category_map` from user input (e.g. a settings UI where a user types a lowercase rule) — categorization will silently degrade to 'other' instead of applying the rule or raising an error, and nothing in the code or tests catches this mismatch between documented and actual behavior.

*Verified: Read ledgerly/importers.py:81-82 — `desc.upper().startswith(prefix)` normalizes only `desc`, never `prefix`. Confirmed via execution: `category_for('COFFEE CO', {'coffee': 'food'})` and `category_for('COFFEE CO', {'Coffee': 'food'})` both return 'other' (DEFAULT_CATEGORY) instead of 'food', while only `{'COFFEE': 'food'}` (already uppercase) works. This directly contradicts the 'case-insensitive prefix rules' claim in both the module docstring (lines 9-10) and category_for's own docstring (lines 78-79). Grep confirms no normalization of `prefix` exists anywhere in the function or file.*
