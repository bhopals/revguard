The one-sentence version

We built RevGuard: a code-review agent pipeline whose defining rule is that no finding reaches a human unless a second, adversarial agent has tried to disprove it — by actually running the code — and failed. And because a claim like "our reviewer is good" is worthless without proof, we also built the benchmark that measures it, and the measurements are the real story.

The problem (who and why)

Senior code reviewers are the bottleneck on engineering teams. CI only catches what tests cover; humans catch what tests miss. Existing AI review bots fail in a specific, well-known way: they spray plausible-sounding comments, most wrong or irrelevant, engineers learn within a week that the bot cries wolf, and then they ignore it. So the goal isn't "find more issues" — it's "only tell me things that are true, with evidence."

The three big pieces

1. The benchmark (target_repo/, target_repo_pro/, cases/). You can't measure a reviewer without ground truth, so we wrote one: Ledgerly, a working expense-tracker app (pure Python + sqlite, full test suite), and 22 pull requests against it containing 61 deliberately seeded, labeled defects — SQL injection, money-through-float corruption, a JOIN that lost its month filter, invite codes that never expire, tests literally written to dodge the bug they're named after. Two PRs are completely clean (to catch bots that invent problems). Crucially, every case's test suite passes — the benchmark measures exactly what CI misses. Six "tier-3" cases are large multi-file PRs with cross-module bugs invisible from the diff alone; that's the hard regime.

2. The pipeline (agent/). Three specialist reviewer agents (correctness+robustness, security, test-adequacy) run in parallel — each gets the diff plus the full repo with read/grep tools, because some bugs only exist relative to code the diff doesn't touch. Their findings are merged, then each one goes to the adversarial verifier: a fresh agent in a sandboxed copy of the repo, with a shell, told to prove the claim wrong. It writes little reproduction scripts — for one bug it literally opened the database twice and caught the crash CI never sees. Only findings that survive both a truth check and a policy check ("would a staff engineer block the merge on this, or is it just advice?") make the final report.

3. The measurement (baseline/, eval/, results/). The fair baseline is what people actually do today: paste the diff into the same model with one prompt. Same cases, same scoring rule (fixed before any system ran), everything traceable to JSON files.

What we found (this is your video's spine)

1. The base model has solved small-PR review. The one-prompt baseline found 39/39 defects on the small cases. We report that instead of hiding it — building agent machinery there is pure overhead.
2. Where review is hard, the pipeline wins on everything. On the six large tier-3 PRs: F1 0.930 vs 0.884, better recall, better precision, fewer false positives.
3. The pipeline is stable; the baseline is not. We ran both twice, fresh. RevGuard's numbers were identical both runs — exactly 3 false positives each time. The baseline's false positives tripled between runs (6 → 18). That run-to-run noise is the cry-wolf failure mode, quantified.

The journey (the changelog — judges weight this heavily)

It was not a straight line, and we documented every step with measurements: v1 (tools + a cautious prompt) was worse than the baseline. v3's verifier confirmed 54 of 54 findings — a rubber stamp, because most bad review comments are factually true ("there are no tests for X") and truth was the only gate. The experiment we added expecting failure (a nitpick reviewer) instead found 11 bugs the specialists missed — proving the specialists' calibration, not their specialization, was the problem. v5 combines all three lessons: permissive reviewers, a robustness owner, and a verifier that gates on truth and policy.

Plus: revguard.py runs the whole pipeline on any real git repo (it reviewed its own commit — approved, zero invented findings), and dogfooding it caught two real bugs in our own CLI.
